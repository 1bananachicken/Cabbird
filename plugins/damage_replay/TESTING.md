# Damage Replay 验证指南

这个插件的行为只能在游戏里验证：它挂钩的是游戏自己的伤害入口。本文给出**逐步验证顺序**，
以及每个计数器到底能证明什么。

---

## 一、装好并启用

1. 构建 + 安装：`.\build.cmd`（仓库根目录，**不要**加 `--parallel`）；
2. 确认包完整 —— 缺 `locales/zh-CN.json` 不会报错，只会**静默**显示英文：

   ```
   .build\windows-vs2022\game-package\Cabbird\plugins\DamageReplay\
       plugin.dll
       manifest.json
       locales\zh-CN.json
   ```

3. 启用插件：宿主 UI 的插件页勾选，或在 `Cabbird\config\plugin-enablement.json` 里写
   `"cabbird.damage-replay": true`。**默认是不启用的**（`defaultEnabled: false`），没启用时插件被
   发现、被编目、然后被刻意不加载 —— 那看起来很像"包被拒了"，但不是。

## 二、验证顺序（从"改不坏东西"到"改得动"）

### 第 1 步 · 先把重放次数设成 1，只验通路

次数 = 1 时 detour 只调用原函数一次，**行为与不装插件完全相同**（`plugin.cpp:429`：`effective = repeats`，
而 1 次就是原始的一次调用）。这一步验证的是"挂上了没有"，不是"有没有效果"。

打开窗口（标题 `Damage Replay`），勾选「启用」，进游戏打一下怪，看计数器：

| 现象 | 结论 | 下一步 |
| --- | --- | --- |
| `calls` **不涨** | hook 没挂上或挂错了目标 | 看状态行；`GameAssembly.dll 未加载` / `创建被拒绝（状态 N）` 会说明原因 |
| `calls` 涨，`replayed` 为 0 | 通路正常（次数 = 1，本来就不该重放） | 进第 2 步 |
| 状态行一直没有内容 | 正常：状态行只在有事可说时绘制（`plugin.cpp:697-704`） | —— |

`calls` 对世界里**每一个**伤害元素都会涨 —— 玩家的、怪的、宠物的、持续伤害的
（`OnExecuteDamageElement` 就是这么被调用的）。所以"被怪打一下 `calls` 也涨"是**预期**，不是异常。

### 第 2 步 · 验证方向过滤（这一步最重要，也最容易被跳过）

**站着不动，让怪打你。** 预期：`calls` 涨，`refused`（已拒绝传入）**也涨**，而 `replayed` 不涨。

方向过滤读的是声明参数 `element` 上的字段（`p_sourcePlayerEntityID`，`+0x54`），不是 `this`；
读错位置会让"怪打玩家"的伤害也被重放，所以这一步值得单独做：

| 现象 | 结论 |
| --- | --- |
| 被怪打时 `refused` 在涨 | 过滤在读正确的位置 |
| 被怪打时 `calls` 涨、`refused` **始终为 0** | **过滤没生效** —— 立刻取消勾选停用，把现象记录下来 |

### 第 3 步 · 才轮到重放次数

在**自己的**伤害上把次数设成 2（不要一上来就 1024），打一下怪，看：

- `replayed` 每次命中增加 `N-1`；
- 伤害飘字/血条是否按预期变化（见第四节：这里有两种可能的结果，只有一种说明插件真的有用）。

次数可以随时改，**下一次命中生效**，不需要关掉再打开开关（detour 每次调用都重新读这个值）。

### 第 4 步 · 加大之前先想清楚

上限是 1024。重放 = 把游戏自己的伤害结算函数跑 1024 次，风险不是线性的：网络同步、伤害记录累积、
UI 刷屏都跟着走。建议 2 → 5 → 10 逐步来，每一步都看一眼游戏是否稳定、`calls`/`replayed` 是否还在涨。

## 三、计数器怎么读

| 计数 | 含义 | 出处 |
| --- | --- | --- |
| `calls` | detour 被调用的次数（**过滤之前**就 +1，所以包含被拒绝的传入伤害） | `plugin.cpp:423` |
| `replayed` | 额外多调用的次数累计（每次命中 +`effective-1`） | `plugin.cpp:433-436` |
| `refused` | 因为"不是玩家发起的伤害"而被压回 1 次的次数 | `plugin.cpp:430-432` |

**这三个数不能证明伤害真的打出去了。** 它们是调用计数器：能证明 hook 在跑、能证明传入伤害被拦下；
伤害元素不携带受击者指针（只有实体 ID，需要游戏自己的解析器），所以插件看不到、也不显示目标 HP
（`plugin.cpp:44-49`）。**唯一的证据是目标血条。**

## 四、结果判读

| 现象 | 结论 |
| --- | --- |
| 伤害飘字与怪血条**都**按重放次数变化 | 重放真的让游戏多结算了几次伤害 |
| 飘字变了、血条掉速**不变** | 服务器权威：本地多跑几次结算不改最终 HP。`AliveProperty.SetHp` 的调用点没有一个落在伤害路径上 |
| 什么都不变 | 回到第 1 步看 `calls` |

第二种结果是这个游戏的设计，不是插件写错了。

## 五、回滚

从轻到重：

1. **取消勾选「启用」** —— 请求移除 detour，恢复原函数（`plugin.cpp:497-508`）；
2. **在宿主里禁用插件** —— 插件停止，hook 交给宿主的 scope ledger 回收；
3. **删掉状态文件回到出厂默认**：

   ```
   Cabbird\state\plugins\cabbird.damage-replay\damage-replay.txt
   ```

   内容只有一行 `replay_count=<整数>`。删掉它，下次加载就用默认值 10（`plugin.cpp:549-553`）。

次数是**自动保存**的，而且只在一个时刻保存：插件停止时（`plugin.cpp:568-578`）。所以游戏进程被强杀
时，最后一次改动**可能没有落盘** —— 这是设计上的取舍。
